IAM policy evaluation logic — decision flow

Step 1 — Explicit DenyExplicit Deny anywhere in any applicable policy = DENY. No exceptions whatsoever.
Step 2 — SCPsService Control Policies define maximum permissions. Must allow the action or it's denied. Applies to all member accounts.
Step 3 — Resource PolicyIf present and grants principal access, Allow may apply even without identity policy (same-account only).
Step 4 — Identity PolicyIAM user/role policy must explicitly Allow the action.
Step 5 — Perm BoundaryPermission Boundaries constrain maximum effective permissions. Must also allow.
DefaultImplicit Deny — all access denied unless explicitly allowed.

IAM principals

  • Root account — unrestricted; protect with MFA; never use for daily ops
  • IAM Users — long-term credentials (password + access keys)
  • IAM Roles — short-term creds via STS; preferred for all workloads
  • IAM Groups — attach policies to multiple users; NOT a principal in policies
  • Federated identities — SAML 2.0, OIDC, Cognito, AWS SSO
  • Service principals — AWS services acting on your behalf (e.g., ec2.amazonaws.com)

Credential types & risk

  • Access Key ID + Secret — programmatic; rotate ≤90 days; never hardcode
  • Short-term STS creds — always preferred; expire automatically
  • Instance profiles — attach roles to EC2; no long-term creds needed
  • IRSA — EKS pods assume role via OIDC per service account
  • Credential Report — lists all users + key age, MFA status, last used
  • IAM Access Analyzer — identifies external access; unused access findings

Trust policy vs. permissions policy Classic exam trap

Trust Policy — Who can assume this role
  • Attached to IAM Role as the "trust relationship"
  • Specifies Principal allowed to call sts:AssumeRole
  • Can trust AWS account, IAM user, role, service, SAML IdP, OIDC
  • Cross-account: requires trust in role + identity policy in source account
Permissions Policy — What the role can do
  • Identity-based policy defining allowed actions on resources
  • Evaluated after trust relationship is established
  • Subject to SCPs and permission boundaries
  • Both policies must align for access to succeed

All 7 policy types — evaluated in this order

Policy TypeScopeAttached ToKey CharacteristicExam Focus
SCP Service Control Policy Org-level OU or Account Sets max permissions; does NOT grant access. Root user is restricted. SCP Deny; does not apply to management account or service-linked roles
Identity-based Account-level User, Role, Group Grants permissions to principal. Managed (AWS/Customer) or Inline. AWS Managed vs Customer Managed vs Inline differences
Resource-based Resource-level S3, SQS, KMS, Lambda, SNS Specifies who (Principal) can access. Cross-account requires both sides allow. Cross-account without role assumption; KMS key policy requirement
Permission Boundary Account-level IAM User or Role only Max permissions a principal can have. Does NOT grant access by itself. Delegated admin scenario; prevent privilege escalation
Session Policy Session-level Passed during AssumeRole Restricts that session only. Cannot expand beyond role's permissions. Scoping down temporary credentials for specific task
ACL Resource-level S3 buckets/objects, VPC Legacy; cannot specify IAM principals, only AWS accounts. S3 Object Ownership; when to disable ACLs
Endpoint Policy VPC Endpoint Gateway/Interface endpoints Controls which principals/resources reachable from VPC. Does not replace bucket policy. Restrict S3 access to within-VPC only

Policy structure — critical fields

  • Version — always "2012-10-17"; required for policy variables
  • Effect — Allow or Deny; Deny overrides Allow
  • Principal — who (only in resource-based + trust policies)
  • Action — service:operation; supports wildcards
  • Resource — ARN; "*" = all resources
  • Condition — evaluated last; must be true for statement to apply
  • NotAction/NotPrincipal/NotResource — inverse matching; dangerous if misused

High-value condition keys

  • aws:SourceIp — by caller IP; NOT for AWS service calls from within AWS
  • aws:SourceVpc / aws:SourceVpce — restrict to VPC or specific endpoint
  • aws:PrincipalOrgID — restrict to principals in your AWS Organization
  • aws:RequestedRegion — restrict to specific regions (SCP use case)
  • aws:MultiFactorAuthPresent — enforce MFA for sensitive actions
  • sts:ExternalId — confused deputy protection in cross-account roles
  • aws:PrincipalTag / aws:ResourceTag — ABAC; dynamic tag-based access
  • aws:CalledVia — restrict to calls made through specific AWS services

Permission Boundaries — deep dive High-frequency exam topic

PurposeDelegate IAM management without risk of privilege escalation. Caps what delegated user/role can ever do.
EvaluationEffective permissions = intersection(identity policy, permission boundary). Both must allow the action.
ScopeOnly applies to IAM users and roles. Does NOT affect resource-based policies or service-linked roles.
Key ScenarioDev team can create IAM roles, but boundary prevents them from granting Admin access — even if their own policy allows it.
Exam trap: A permission boundary does NOT grant permissions — it only limits them. The role needs BOTH the identity policy AND the boundary to allow.

AWS STS — Security Token Service

  • AssumeRole — same/cross-account; returns temp creds (15min–12hr, default 1hr)
  • AssumeRoleWithSAML — federate via SAML 2.0 IdP (ADFS, Okta); console SSO
  • AssumeRoleWithWebIdentity — OIDC-based; Cognito/IRSA; prefer Cognito for mobile
  • GetSessionToken — IAM user + MFA; returns temp creds with same permissions
  • GetFederationToken — up to 36hr; legacy pattern, avoid in modern arch
  • ExternalId — passed in AssumeRole to prevent confused deputy attacks
  • Regional STS — recommended for resilience; must enable per region

AWS IAM Identity Center (SSO) Modern standard

  • Centralized SSO for all AWS accounts in Organization + SAML apps
  • Permission Sets — define IAM policies provisioned into each account
  • Identity sources: built-in directory, AWS Managed AD, AD Connector, external IdP via SCIM + SAML
  • SCIM provisioning — auto-sync users/groups from IdP (Okta, Azure AD)
  • ABAC support using IdP attributes in permission sets
  • Multi-account access without creating IAM users per account
  • Formerly "AWS SSO" — renamed to IAM Identity Center in 2022

Amazon Cognito

  • User Pools — user directory; sign-up/sign-in, MFA, federation; issues JWTs
  • Identity Pools — exchanges tokens (User Pool, Google, SAML) for AWS STS creds
  • Unauthenticated identities — guest access with limited AWS permissions
  • Enhanced vs basic authflow — enhanced: Cognito manages role selection
  • Token validity: ID/Access tokens 1hr default; refresh token up to 10 years
  • Exam pattern: mobile/web app needing AWS resource access → Cognito Identity Pool + STS

IAM Access Analyzer

  • Identifies resources accessible from outside your zone of trust (account or Org)
  • Supported resources: S3, IAM roles, KMS keys, Lambda, SQS, Secrets Manager, SNS
  • External access findings + unused access findings
  • Policy validation — checks against IAM best practices, security warnings, errors
  • Policy generation — generates least-privilege policy from CloudTrail activity
  • Archive rules — suppress expected/approved external access findings
  • Unused access analysis — roles not used in 90+ days flagged for review

AWS Directory Service

  • AWS Managed Microsoft AD — full AD in AWS; supports trusts to on-prem AD
  • AD Connector — proxy to on-prem AD; no users stored in AWS; MFA via RADIUS
  • Simple AD — Samba-based; no trusts; small deployments only
  • Trust types: one-way (outgoing/incoming), two-way, forest vs external
  • Used by: IAM Identity Center, WorkSpaces, RDS (Windows auth), FSx for Windows
  • Exam: on-prem users → AWS → AD Connector or Managed AD + Identity Center

AWS Organizations & SCPs

  • Management account — root of org; NOT subject to SCPs
  • SCPs apply to all principals (including root user) in member accounts
  • SCPs do NOT apply to service-linked roles
  • FullAWSAccess — default SCP allowing all; add Deny SCPs on top
  • Allow-list: remove FullAWSAccess, add explicit Allows (tightest)
  • Deny-list: keep FullAWSAccess, add explicit Denies (most common)
  • Effective access = SCP Allow ∩ IAM Policy Allow

Cross-account access patterns High exam weight

PatternMechanismWhen to Use
Role assumption (sts:AssumeRole) Account A assumes role in B. Trust policy in B + identity policy in A must both allow. Standard cross-account EC2/Lambda/human access. Preferred method.
Resource-based policy (direct) Account B resource policy grants Account A principal directly. No role switch. S3, SQS, SNS, KMS cross-account. Service-to-service patterns.
Cross-account + ExternalId Third party must supply ExternalId in AssumeRole call. Prevents confused deputy. Third-party SaaS/vendor integration into your account.
Resource Access Manager (RAM) Shares AWS resources (subnets, Transit GW, Route53) across accounts in Org. Shared VPC networking, centralized security tooling.

ABAC vs RBAC

RBAC — Role-Based Access Control

  • Access based on IAM role/group membership
  • Scale problem: N roles × M resources = policy explosion
  • Valid for coarse-grained, stable access patterns

ABAC — Attribute-Based Access Control

  • Access based on tags on principal AND resource
  • Use aws:PrincipalTag + aws:ResourceTag in conditions
  • Single policy scales to thousands of resources automatically
  • Requires consistent tagging strategy across org
  • Exam: "scale IAM without new policies per resource" → ABAC
Classic ABAC: Allow action if aws:PrincipalTag/Project equals aws:ResourceTag/Project

Privilege escalation vectors

iam:CreatePolicyVersionCreate new version with Admin perms + set as default. Mitigate: deny SetDefaultPolicyVersion separately.
iam:AttachUserPolicyUser attaches AdministratorAccess to themselves. Require permission boundary on delegated IAM admins.
iam:PassRoleUser passes privileged role to Lambda/EC2. Restrict iam:PassRole to specific role ARNs. Frequently tested.
sts:AssumeRole *Wildcard trust allows any principal. Always specify exact principals in trust policy.
CreateAccessKey (others)User creates key for another user and exfiltrates. Audit with IAM Access Analyzer + Credential Report.

Federation deep dive

SAML 2.0 federation

  • IdP authenticates user → SAML assertion → STS validates → issues temp creds
  • Requires IAM SAML Provider + trust in role
  • Console: AssumeRoleWithSAML → AWS sign-in endpoint redirect
  • SAML attributes map to IAM role via RoleSessionName, Role ARN attributes

OIDC federation

  • IdP issues JWT → STS validates signature against OIDC provider → issues creds
  • Use cases: GitHub Actions CI/CD, IRSA (EKS), public IdPs
  • Thumbprint required when creating OIDC provider in IAM

Compute IAM patterns

  • EC2 instance profile — attached role; creds via IMDS (169.254.169.254)
  • IMDSv2 required — prevents SSRF-based metadata theft; enforce hop limit 1
  • Lambda execution role — what Lambda can access; resource policy = who invokes
  • ECS task role — app permissions (what the container does)
  • ECS task execution role — ECS agent permissions (ECR pull, CloudWatch Logs)
  • IRSA (EKS) — pod annotation + OIDC provider → AssumeRoleWithWebIdentity per pod
  • Service-linked roles — not subject to SCPs or permission boundaries

High-frequency exam questions & answers

Q1. A user has an IAM policy allowing s3:DeleteObject. An SCP on the account denies s3:DeleteObject. What is the result?
Access is DENIED. SCPs are evaluated before identity policies. The SCP Deny overrides any IAM policy Allow. Effective permission is the intersection of SCP permissions AND identity policy permissions.
Q2. Allow IAM user in Account A to access S3 bucket in Account B without assuming a role. How?
Add a resource-based bucket policy in Account B explicitly granting the Account A IAM user access. Also ensure Account A has an identity policy allowing the S3 action. For cross-account with resource-based policies, BOTH the resource policy (Account B) AND identity policy (Account A) must allow the action.
Q3. Developer needs to create IAM roles but must NOT create a role with AdministratorAccess. Recommended solution?
Attach a Permission Boundary to the developer's IAM role that excludes AdministratorAccess. Additionally, require the developer to always apply that same boundary when creating new roles (enforce via IAM condition iam:PermissionsBoundary). This prevents privilege escalation through role creation even if their own policy allows iam:CreateRole.
Q4. A third-party vendor needs access to your AWS account. Prevent the confused deputy problem. How?
Create an IAM role with the vendor's account in the trust policy. Require an sts:ExternalId condition. The vendor must pass this ExternalId (a shared secret between you and that specific vendor) when calling AssumeRole. This ensures only your vendor instance can assume the role, not other customers of the same vendor.
Q5. EC2 in private VPC should only access S3 within the same account. Enforce this.
Create a Gateway VPC Endpoint for S3. Attach an endpoint policy restricting access to your account's buckets only. Add a bucket policy condition using aws:SourceVpce to deny requests not from the VPC endpoint. Traffic stays within AWS network and is account-scoped.
Q6. Prevent any IAM user from disabling CloudTrail across all accounts. Most scalable solution?
Create an SCP at the root OU level (or all member OUs) explicitly denying cloudtrail:DeleteTrail, cloudtrail:StopLogging, and cloudtrail:UpdateTrail. SCPs apply to all principals in all member accounts. Note: the management account is exempt from SCPs — protect it separately with IAM policies and strict MFA enforcement.
Q7. On-premises AD users need AWS Management Console access. Recommended architecture?
Deploy IAM Identity Center connected to AWS Managed Microsoft AD (with AD trust to on-prem) or AD Connector (proxy mode). Users authenticate to on-prem AD → IAM Identity Center provisions access via Permission Sets. No IAM users created per account. Centralized, scalable, and supports MFA via AD.
Q8. An IAM role has all S3 actions allowed. A session policy passed during AssumeRole only allows s3:GetObject. What can the session do?
Only s3:GetObject. Session policies can only restrict — never expand — beyond the role's identity policy. Effective session permissions = intersection(role policy, session policy). Session policies are evaluated last and act as an additional filter.
Q9. Lambda in Account A needs to call KMS in Account B. How do you configure this?
Two requirements: (1) KMS key policy in Account B must grant the Lambda's execution role ARN permission to use the key (kms:Decrypt, kms:GenerateDataKey etc.). (2) Lambda's execution role in Account A must have an IAM policy allowing the kms actions on that specific key ARN. KMS cross-account requires BOTH key policy AND identity policy to allow — unlike S3 where one side can be sufficient in same-account.
Q10. You need to scale IAM access to thousands of S3 buckets without creating a new policy for each bucket. Solution?
Implement ABAC (Attribute-Based Access Control). Tag all S3 buckets with consistent tags (e.g., Project, Environment). Tag IAM roles with matching tags. Create one policy with conditions: StringEquals: { "aws:PrincipalTag/Project": "${aws:ResourceTag/Project}" }. This single policy dynamically permits access when principal tags match resource tags — no new policies needed for new buckets.

Frequently asked — conceptual clarifications

Can an SCP grant permissions?
No. SCPs only define the maximum permissions available — they act as guardrails (a ceiling). They never directly grant permissions. A principal also needs an identity-based or resource-based policy that allows the action. Think of SCPs as a ceiling, not a key.
Does the SCP apply to the management account?
No. The management (root/payer) account is NOT subject to SCPs. This is a critical exam point. SCPs only apply to member accounts and their OUs. Protect the management account separately using strict IAM policies and MFA enforcement.
What is the difference between IAM Identity Center and IAM SAML federation?
IAM SAML federation (AssumeRoleWithSAML) requires manually creating IAM roles and mapping SAML attributes in EACH account. IAM Identity Center centralizes this — one IdP integration, Permission Sets automatically provisioned to all accounts. Identity Center is the recommended modern approach for multi-account orgs. Use IAM SAML federation for specific custom/legacy integrations.
What is a service-linked role?
A pre-defined IAM role by an AWS service with exactly the permissions that service needs to call other AWS services on your behalf. Created automatically when you enable the service. You cannot modify its trust policy or permissions. Cannot be deleted while associated resources exist. NOT subject to SCPs or permission boundaries. Examples: AWSServiceRoleForECS, AWSServiceRoleForAutoScaling.
Same-account: if both identity policy and resource policy exist, do both need to allow?
No — same-account is more permissive. If EITHER the identity policy OR the resource policy allows the action (and no explicit Deny exists), access is granted. Cross-account is stricter: BOTH the identity policy in the source account AND the resource policy in the target account must allow the action.
What is IMDSv2 and why does it matter for IAM security?
IMDSv1 allows simple GET requests to fetch IAM role credentials from EC2 metadata, exploitable via SSRF. IMDSv2 requires a session-oriented PUT request with a token first (preventing SSRF exploitation). Enforce via EC2 launch settings, AWS Config rule (ec2-imdsv2-check), or SCP denying ec2:RunInstances when HttpTokens is not "required".
How does IRSA work for EKS pods?
An OIDC provider is configured in IAM for the EKS cluster. Pod service accounts are annotated with a role ARN. The EKS pod receives a projected service account token, then calls AssumeRoleWithWebIdentity. The IAM role trust policy trusts the cluster's OIDC provider with a condition matching the namespace/service account. Each pod gets its own scoped AWS credentials — no shared node-level IAM role.
KMS key policy — what's unique vs other resource policies?
KMS does NOT automatically grant the account root or admin access to a key — unlike S3 or SQS. If no key policy exists, nobody can use the key. The default KMS key policy must explicitly grant kms:* to the account root so IAM policies can further delegate access. This makes KMS key policy management critical and a frequent exam topic.

Top exam gotchas & traps Read carefully

Gotcha 1IAM Groups are NOT principals — you cannot reference a group in a resource-based policy or trust policy. Groups are only for attaching policies to multiple users.
Gotcha 2Permission boundaries do NOT grant permissions — they only restrict. Need both boundary AND identity policy to allow.
Gotcha 3SCPs do NOT apply to the management account or service-linked roles. Frequently used as distractors.
Gotcha 4Cross-account S3: if role assumption is used, only the assumed role's identity policy needs to allow S3. If using direct resource policy cross-account, both sides must allow.
Gotcha 5aws:SourceIp doesn't work for AWS service calls (Lambda→S3, EC2→S3). Use aws:VpcSourceIp or aws:SourceVpce instead.
Gotcha 6NotAction with Effect: Allow is dangerous. "Allow NotAction: sts:AssumeRole" allows EVERYTHING except that action — easy to over-permit. Prefer explicit allow lists.
Gotcha 7IAM policy size limits: inline policy max 2KB (user), 5KB (role), 10KB (group). Managed policy max 6,144 chars. Up to 5 managed policy versions stored.
Gotcha 8S3 Block Public Access (BPA) is separate from bucket policies/ACLs and overrides them. Even if bucket policy allows public access, BPA blocks it at account or bucket level.
Gotcha 9KMS does NOT auto-grant account root access. Key policy must explicitly grant it. If no key policy exists, nobody can use the key — even the account admin.
Gotcha 10GetSessionToken does NOT reduce permissions — returns creds with same permissions as the calling IAM user. Use session policies (passed during AssumeRole) to scope down.

Quick decision tree — which policy type to use?

  • Restrict entire Org from dangerous actions → SCP at root/OU level
  • Delegate IAM management without privilege escalation risk → Permission Boundary
  • Cross-account S3/SQS/KMS without role switch → Resource-based policy
  • Cross-account EC2/Lambda/ECS access → IAM Role + AssumeRole
  • Scope down role permissions for one specific task/session → Session Policy
  • Scale access to thousands of resources without new policies → ABAC (PrincipalTag + ResourceTag)
  • On-prem AD users → multi-account AWS access → IAM Identity Center + AD Connector/Managed AD
  • Mobile/web app needing AWS resource access → Cognito Identity Pools
  • EKS pod needs scoped AWS permissions → IRSA (IAM Roles for Service Accounts)
  • Prevent metadata credential theft on EC2 → Enforce IMDSv2 (HttpTokens=required)
  • Third-party vendor access — prevent confused deputy → Role + sts:ExternalId condition
  • Discover external access to your resources → IAM Access Analyzer
