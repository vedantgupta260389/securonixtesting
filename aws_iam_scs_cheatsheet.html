Core IAM entities

  • Users — long-term credentials (access keys, password)
  • Groups — attach policies to multiple users; cannot nest groups
  • Roles — temporary credentials; assumed by services, users, or federated identities
  • Policies — JSON permission documents attached to entities

Exam focus Policy types

  • Identity-based — attached to users/groups/roles
  • Resource-based — attached to resources (S3 bucket policy, KMS key policy)
  • SCPs — org-level guardrails (do NOT grant, only limit)
  • Permission boundaries — max permissions for an entity
  • Session policies — passed at AssumeRole time
  • ACLs — legacy, cross-account S3/object control

Auth Auth & federation

  • SAML 2.0 — enterprise SSO (ADFS, Okta)
  • OIDC — web/mobile (Cognito, GitHub Actions)
  • Cognito Identity Pools — guest + authenticated access to AWS
  • AWS SSO / IAM Identity Center — multi-account SSO

Audit Monitoring & compliance

  • CloudTrail — who did what & when (API calls)
  • IAM Access Analyzer — finds unintended external access
  • Credential report — all users + credential status
  • Access Advisor — last service usage per entity
  • Config rules — detect non-compliant IAM settings

IAM evaluation hierarchy

Explicit Deny→ wins always → SCP→ Perm boundary→ Session policy→ Identity policy→ Resource policy→ Default DENY
All applicable policies must allow (except for cross-account: resource policy alone can grant if it specifies the principal's account).

Policy structure (JSON)

  • Version — always "2012-10-17"
  • Statement — array of permission blocks
  • Effect — Allow or Deny
  • Action — API operations e.g. s3:GetObject
  • Resource — ARN of the target resource
  • Principal — who (only in resource-based & trust policies)
  • Condition — optional conditional logic

Managed vs inline

  • AWS managed — pre-built, versioned by AWS
  • Customer managed — your own reusable policies
  • Inline — embedded in one entity; deleted with entity

Policy limits

  • Managed policy max size: 6,144 chars
  • Inline policy max: 2,048 chars per entity
  • 10 managed policies per user/group/role

Condition operators (exam fav)

  • StringEquals / StringLike (wildcards)
  • ArnLike — match ARN patterns
  • IpAddress — source IP range
  • Bool — aws:SecureTransport, aws:MultiFactorAuthPresent
  • DateLessThan — time-bound access
  • Null — check if key exists
  • aws:PrincipalOrgID — restrict to your org

Permission boundary rules

  • Sets the maximum permissions; doesn't grant anything itself
  • Effective permission = intersection of identity policy AND boundary
  • Used to delegate admin safely (devs can create roles but not exceed boundary)
  • Does not limit resource-based policies or SCPs
Boundary + no identity policy = no permissions even if boundary allows everything.

SCPs — key rules

  • Applied to accounts/OUs in AWS Organizations
  • Do NOT grant permissions — only restrict
  • Do NOT affect management account
  • Do NOT affect service-linked roles
  • Default SCP FullAWSAccess allows everything
  • Deny in SCP blocks even the account root user for that service
  • Inheritance: child OUs inherit parent SCP denies
  • Use aws:RequestedRegion to restrict regions via SCP

Role components

  • Trust policy — who can assume the role (Principal)
  • Permission policy — what the role can do
  • Session duration — 1h default, up to 12h (role setting)
  • External ID — prevents confused deputy in cross-account

STS API calls

  • AssumeRole — assume a role (same or cross-account)
  • AssumeRoleWithSAML — SAML federation
  • AssumeRoleWithWebIdentity — OIDC federation
  • GetSessionToken — MFA-enforced short-term creds
  • GetFederationToken — long-term for federated apps

Cross-account access flow

Account A user → calls AssumeRole → Role in Account B
Trust policy must list Account A principal
Account A identity policy must allow sts:AssumeRole
Resource policies (S3, KMS) can grant cross-account without AssumeRole if the source account's identity policy also allows it.

Instance profiles & service roles

  • Instance profile — container for an IAM role attached to EC2
  • EC2 gets creds via IMDSv2 (169.254.169.254)
  • Service-linked roles — pre-defined for AWS services; cannot edit trust policy
  • Lambda, ECS tasks get role via task/execution role ARN

IAM Identity Center (SSO)

  • Centralized access for multi-account and apps
  • Supports SAML/SCIM for external IdPs
  • Permission sets — map to IAM roles in each account
  • Replaces account-level IAM users for human access
  • Attribute-based access control (ABAC) via user attributes
  • Temp credentials dispensed per session
  • Best practice: use over individual IAM users
  • Session duration controlled per permission set

Evaluation logic — same account

  • Explicit Deny anywhere → final answer: DENY
  • SCP must allow (if Orgs used)
  • Permission boundary must allow (if set)
  • Session policy must allow (if AssumeRole with policy)
  • Identity policy OR resource policy must allow
  • Otherwise → implicit DENY

Evaluation logic — cross-account

  • Both accounts must grant access
  • Account A: identity policy allows sts:AssumeRole on role B
  • Account B: role trust policy allows account A principal
  • For resource policies: requester's identity policy must allow too
  • SCP in both orgs must not deny
Resource policy alone in cross-account ≠ sufficient without identity policy allowing it.

ABAC (attribute-based AC)

  • Use tags on resources and IAM principals
  • Condition: aws:ResourceTag/team = aws:PrincipalTag/team
  • Scales without modifying policies as teams grow
  • Works with IAM Identity Center attribute mappings

Confused deputy prevention

  • Occurs when a service is tricked into acting on another account's behalf
  • Fix: use aws:SourceArn or aws:SourceAccount in role trust policy
  • Fix: require ExternalId in cross-account trust (3rd-party integrations)
Always use sts:ExternalId when allowing 3rd-party vendors to assume your roles.

Effective permissions matrix

With SCP

  • SCP Allow + Identity Allow = ✓ Allow
  • SCP Deny + Identity Allow = ✗ Deny
  • SCP Allow + Identity Deny = ✗ Deny

With boundary

  • Boundary Allow + Identity Allow = ✓ Allow
  • Boundary Deny + Identity Allow = ✗ Deny
  • Boundary Allow + no Identity = ✗ Deny

Resource policies

  • Same acct: Identity OR Resource policy = ✓ Allow
  • Cross-acct: BOTH required
  • S3 ACLs legacy; prefer bucket policies

IAM Access Analyzer

  • Detects resources shared outside your zone of trust
  • Supported: S3, IAM roles, KMS keys, Lambda, SQS, Secrets Manager, SNS
  • Generates least-privilege policies from CloudTrail logs
  • Validates policies against IAM policy grammar and best practices
  • Zone of trust = account or AWS Organization

CloudTrail for IAM

  • Logs all IAM API calls (management events by default)
  • Key events: AssumeRole, CreateUser, AttachPolicy
  • Use EventBridge to trigger alerts on sensitive actions
  • S3 + Athena for ad-hoc investigation
  • Enable log file validation to detect tampering

AWS Config for IAM

  • Managed rules: iam-password-policy, iam-root-access-key-check, mfa-enabled-for-iam-console-access
  • Detect drift from security baseline continuously
  • Aggregator for multi-account compliance view
  • Remediation with SSM Automation

Secrets Manager vs Parameter Store

  • Secrets Manager — auto-rotation, cross-account, RDS/Redshift native integration
  • SSM Parameter Store — free tier, no auto-rotation, use for non-secret config
  • Both use IAM resource-based policies for access control
  • Secrets Manager supports resource policies natively

KMS + IAM integration

  • KMS key policy is the primary access control mechanism
  • Key policy must explicitly give account root access OR it's locked out
  • IAM policy alone not sufficient — key policy must also allow
  • Grants: temporary, vend-able permissions on CMKs
  • kms:ViaService condition — limit key use to specific AWS service
Unlike most services, KMS key policy must explicitly allow the account; IAM alone won't work.

Cognito

  • User Pools — authentication (sign-up/sign-in, JWTs)
  • Identity Pools — authorization (exchange JWT for AWS creds)
  • Supports unauthenticated (guest) roles
  • Enhanced flow vs basic flow for role mapping
  • Attribute mapping from IdP → Cognito attributes

Must know Classic gotchas

  • SCPs do NOT grant permissions — they only restrict
  • Permission boundary ≠ explicit allow — still needs identity policy
  • Explicit Deny always wins — no exceptions
  • Root user cannot be restricted by SCPs
  • Service-linked roles cannot have trust policies edited
  • IAM is global — not region-specific
  • Groups cannot assume roles; roles cannot be members of groups

Scenario Least privilege patterns

  • Use NotAction with Deny carefully — allows everything else
  • Use aws:PrincipalOrgID to restrict to org only
  • Use aws:SourceVpc / aws:SourceVpce for VPC-only access
  • Use IAM Access Analyzer + CloudTrail to generate least-priv policies
  • Require MFA with aws:MultiFactorAuthPresent: true
  • Tag-based conditions for ABAC at scale

Scenario When to use what

  • Enforce org-wide controls → SCP
  • Delegate admin safely → Permission boundary
  • Cross-account S3 access → Bucket policy + identity policy
  • Temporary elevated access → AssumeRole + session policy
  • Human users → IAM Identity Center
  • App creds → IAM roles (never access keys in code)
  • Find external sharing → IAM Access Analyzer

Quick ref Key condition keys

  • aws:MultiFactorAuthPresent — enforce MFA
  • aws:PrincipalOrgID — org membership
  • aws:RequestedRegion — region restriction
  • aws:SourceIp / aws:VpcSourceIp — network restriction
  • aws:CalledVia — restrict to calls via specific service
  • aws:SecureTransport — enforce HTTPS/TLS
  • sts:ExternalId — confused deputy prevention
  • s3:prefix — S3 path-based access

SCS-C03 IAM domain — common question patterns

Access issues

  • User can't access → check SCP → boundary → identity policy order
  • Cross-account denied → both sides must allow
  • Root can't be denied by SCP (trick Q!)

Design questions

  • Limit devs from creating over-permissive roles → permission boundary
  • Org-wide deny of region → SCP with aws:RequestedRegion
  • Vendor access → ExternalId + least-privilege role

Audit / detect

  • Who assumed a role → CloudTrail AssumeRole events
  • Detect unused permissions → Access Advisor
  • Find public S3 → Access Analyzer + Config rule
